==== Domain Attributes - Settings
:author: Keishlyany Sanabria (@keisanabria)

*Framework:* Schütz-Schmuck, M. (2021). _Domain Attributes_. Department of Computer Science and Engineering, University of Puerto Rico at Mayagüez.

===== Overview

This document characterizes the domain attributes of the app's *Settings* section using the four-category framework from the UPRM domain attributes lecture. The analysis guides future modeling and design decisions by identifying how each setting field behaves with respect to continuity, dynamics, tangibility, and dimensionality.

===== Continuity vs. Discreteness

The lecture defines *discrete* phenomena as those modeled by a map (function on a countable set), where the domain takes on specific values at given states, with transitions triggered by input stimuli. *Continuous* phenomena, by contrast, are modeled by functions over uncountable domains (for example, time). *Hybrid* phenomena combine both.

All settings in the Settings section are *discrete*. Each setting takes on a value from a finite, countable set, and changes only when the user explicitly applies a new value. No setting interpolates between values over time.

The discrete settings break down into three sub-types:

[cols="1,2,1", options="header"]
|===
| Sub-type | Examples | Domain

| *Boolean*
| Push notifications on/off, dark mode enabled/disabled
| `{true, false}`

| *Enumerable*
| Language selection (English, Spanish, French…)
| Finite named set

| *Numeric*
| Font size / text scale (for example, 80%–150%), notification quiet hours (start/end hour)
| Bounded integer or real interval
|===

NOTE: *Modeling implication:* Discrete settings map naturally to `Boolean`, `enum`, and bounded `int`/`float` types. No continuous sampling or interpolation logic is needed.

===== Statics vs. Dynamics

The lecture positions statics and dynamics on a spectrum:

* *Static*: not time-dependent, not affected by events, does not change.
* *Dynamic inert*: changes value only upon an external stimulus; no internal impulse.
* *Dynamic active*: can change on its own internal impulse (autonomous, biddable, or programmable).

====== Static settings (rarely or never change)

These settings capture facts about the user's account or device that are either immutable or change only through a formal process outside the app itself.

[cols="1,2", options="header"]
|===
| Field | Rationale

| Account email address
| Set at registration; changed only via a dedicated account-management flow, not as a routine preference.

| Region / locale
| Reflects the user's actual locale; changes are rare and deliberate.

| Accessibility feature availability
| Determined by device capabilities; the app surfaces but does not control these.
|===

====== Dynamic inert settings (change on user action only)

The majority of user-facing preferences are *dynamic inert*: they hold a stable value indefinitely and transition to a new value only when the user explicitly acts (taps a toggle, selects from a list, saves a form).

[cols="1,2", options="header"]
|===
| Field | Stimulus

| Push notifications enabled
| User toggles the switch

| Preferred language
| User selects from language picker and confirms

| Dark mode / theme
| User selects a theme option

| Notification quiet hours
| User sets start and end times

|===

NOTE: *Modeling implication:* Dynamic inert settings do not need polling or background sampling. A persistent key-value store (for example, `SharedPreferences`, `UserDefaults`, a `settings` database table) is sufficient. Change events are fully determined by user-initiated write operations.

====== Dynamic active settings (not applicable)

No settings in this section exhibit autonomous or biddable behavior, settings do not change themselves in the background without a user action. If a future feature were to sync settings from a remote profile, that sub-system could be classified as *dynamic active programmable*, but the settings values themselves remain inert from the UI domain's perspective.


===== Tangibility

The lecture distinguishes:

* *Humanly / physically tangible*: experienced through the senses or instruments; not fully formalizable.
* *Intangible precise*: concepts from mathematics, program semantics; fully formalizable (for example, numbers, Booleans, sets).
* *Intangible imprecise*: human emotions and subjective states; difficult to formalize.

Settings data is *intangible and precise*. Each setting is an abstract configuration value, it has no physical manifestation that can be measured with an instrument, and its meaning is fully specified by its type and allowed value set.

[cols="1,1,2", options="header"]
|===
| Field | Tangibility classification | Implication

| Push notifications enabled
| Intangible precise (Boolean)
| Validation is exact: only `true`/`false` are valid; no sensor noise or measurement error.

| Preferred language
| Intangible precise (enum / IETF language tag)
| Stored as a well-defined string code (for example, `"en-US"`); no ambiguity in the value itself.

| Notification quiet hours
| Intangible precise (structured time value)
| Represented as exact time values; comparison and ordering are well-defined.
|===

NOTE: *Storage implication:* Because settings are intangible and precise, they can be stored and retrieved without lossy encoding. Validation rules are strict and machine-checkable (type checks, range checks, membership checks against enum sets). There is no need to account for measurement uncertainty.


===== Dimensionality

The lecture defines three levels:

* *Zero-dimensional (atomic)*: a single scalar value; modeled with atomic types (`bool`, `int`, `float`, `enum`).
* *One-dimensional (linear sequence)*: an ordered collection of constituents with forward/backward references; modeled with sets, tuples, or sequences.
* *Multi-dimensional*: recursive or graph-structured; requires forward and backward references and/or recursion.

====== Zero-dimensional settings (atomic values)

Most settings are *zero-dimensional*, they hold a single atomic value with no internal structure.

[cols="1,1,1", options="header"]
|===
| Field | Type | Example value

| Push notifications enabled
| Boolean
| `true`

| Dark mode
| Enum
| `"system"`

| Preferred language
| Enum (string code)
| `"es-PR"`
|===

====== One-dimensional settings (structured but non-recursive)

A small number of settings are *one-dimensional* because their value is a tuple or a bounded collection rather than a single scalar.

[cols="1,1,2", options="header"]
|===
| Field | Structure | Notes

| Notification quiet hours
| Tuple `(start: Time, end: Time)`
| Two related scalar values stored together; order matters.

| Notification channel preferences
| Set of `(channel: enum, enabled: Boolean)` pairs
| A flat collection of per-channel toggles; no recursion.
|===

NOTE: *Modeling implication:* One-dimensional settings require a small record or array type rather than a plain scalar. They should be stored as a single logical unit (for example, a JSON object or a dedicated sub-table) to preserve the relationship between their constituent values.

====== Multi-dimensional settings (not present / flag for review)

No current settings field requires recursive or graph-structured modeling. However, if a future "notification rules" feature allowed conditional logic (for example, "if event type X and time is Y, then do Z"), that field would cross into multi-dimensional territory and would need a more expressive model (for example, a rule tree).

==== Domain Attributes of Lost and Found Reports
:author: Andres Cruz Zapata

Domain phenomena and concepts have diverse attributes that affect the modeling of these concepts as code. This section describes the attributes of reports in the lost and found application, covering the continuity, discreteness, hybridicity, chaos, statics and dynamics,  tangibility, and dimensionality of said reports.

[discrete]
==== Discreteness:
Reports can be viewed as discrete phenomena, taking on specific values for each instance and having their state (ie. open, claimed, returned/closed) change depending on the current state and the external inputs received over time. For example, a lost report might change its state from open to claimed after a user claims the item and it is verified by an admin of the application.

Additionally, within these reports, attributes can be found that can be unique to each instance of a report:

* Report ID
** A unique identifier for each report.
* Category
** ie. personal, electronic, other.
* Report Type
** Lost or Found.
* Status
** The current state of the report; open, claimed, or closed.
* User Id
** The unique id of the user that created the report.

[discrete]
==== Statics and Dynamics:
Static attributes are attributes that generally remain unchanged after creation, while Dynamic attributes can change over time. Reports have both static and dynamic attributes:

* Static
** Item Description
** Item Category
** Location
** Report Creator

* Dynamic
** Report Status

For example, a report's item description should remain static during the full lifecycle of the report. There can be exceptions, such as the description having typos or lacking clarification; in such cases the user may be allowed to edit the report. On the other hand, the report's status will always change over time whether that is when the item is claimed or when the report expires.

Furthermore, a report experiences dynamic inert behavior, which is when a phenomenon changes due to external inputs rather than changing independently over time. Reports can have their status change due to the application's administration verifying and updating the report's status.

[discrete]
==== Tangibility and Intangibility:
Tangible attributes correspond to real physical properties of a phenomenon while intangible attributes correspond to characteristics that only exist within the application's system. Reports have both tangible and intangible attributes:

* Tangible
** Item Photo
** Item Description
** Location Found or Lost

These properties correspond to the real life lost item and therefore considered tangible attributes.

* Intangible
** Report ID
** Report Status

These only exist within the system and have no real ties to the physical item.

[discrete]
==== Dimensionality:
Dimensionality refers to the structural complexity of domain information, ranging from simple atomic values to more complex relationships and data structures.

* Atomic: These are attributes that can be described with simple data types and are composed of single values. Examples:
** Status
** Category
** Date Created

* Linear: These are attributes that relate to each other from forward and backwards references. Example:
** Tags
*** Contain a list of keywords related to the item lost/found.

* Multi-Dimensional: These are concepts that require forward and backward references and/or recursion. Example:
** User-Report Relationship
*** At a higher level, references from both reports and users are needed to tie these phenomena together in order to create relationships, such as ownership or claims.

==== [Lecture Topic Task] Business Procedures Facet Analysis
:author: Omar A. Cordero Maldonado (omar-cordero)

The business procedures facet describes the operational workflows used to manage items within the Lost & Found platform. These procedures define how users interact with the system and how items flow through the platform from the moment they are reported lost or found until they are returned.

Understanding these procedures helps ensure the system supports consistent, reliable, and efficient handling of lost property.

===== Lost Item Reporting Procedure

The lost item reporting procedure describes how a user reports an item they have lost.

Steps typically include:

* The user logs into the platform.
* The user submits a Lost Item Report.
* The report includes relevant information such as item type, description, location, and date and time.
* The system stores the report in the database.
* The system may attempt to identify possible matches with existing found item reports.

This procedure allows users to notify the system that an item is missing and provides information that can later be used to match found items.

*Realistic Example:* A student leaves their calculator behind after a CIIC 3015 exam in the Stefani building. Later that afternoon, they log into the Lost and Found platform and submit a Lost Item Report describing it as a black TI-84 Plus with an anime sticker on the back, last seen in room S-113 on Tuesday at 11:00 AM. The system stores the report and flags a potential match with a found item submitted earlier that day by another studentr who turned in a calculator found in the same room.

===== Found Item Submission Procedure

The found item submission procedure describes how users or staff report items that have been discovered.

Typical steps include:

* A user logs into the platform.
* The finder submits a Found Item Report.
* The report includes details such as the description of the item, location where it was found, date and time found, and an optional photo.
* The system stores the found item entry.
* The item may be physically delivered to a Lost and Found office for storage.

This procedure allows items to enter the Lost and Found system so that owners can locate them.

*Realistic Example:* A student finds an unattended backpack in the bathroom inside the Chardón building after classes. They take it to the Office of Student Affairs and a staff member logs into the platform to submit a Found Item Report. The report notes a black JanSport backpack containing notebooks and a Math Book, found on Wednesday at 2:30 PM in the bathroom near the building entrance. A photo of the backpack is attached to help the owner identify it.

===== Ownership Claim Procedure

The ownership claim procedure describes how users request to retrieve an item they believe belongs to them.

Typical steps include:

* A user searches the platform for items that match their lost item.
* The user submits a Claim Request.
* The claim may require additional verification details such as unique identifying characteristics, serial numbers, or private descriptions not visible in the listing.
* Moderators or staff review the claim.
* If the claim is verified, the item is marked as claimed.

This procedure helps prevent fraudulent claims and ensures items are returned to their rightful owners.

*Realistic Example:* A student searching the platform finds an entry matching their missing backpack. They submit a Claim Request and provide additional details not shown in the public listing, including what's insaide, a keychain attached to the zipper, and the name of the book inside. A staff member reviews the claim, confirms the details match, and marks the item as Claimed.

===== Item Return Procedure

Once ownership has been verified, the item can be returned to the owner.

Typical steps include:

* The owner arranges to retrieve the item.
* Staff verifies the user's identity if necessary.
* The item is returned to the owner.
* The system updates the item status to returned.

Recording returned items ensures the platform accurately reflects the status of each item.

*Campus Example:* The student whose claim was approved visits the Office of Student Affairs during office hours. The staff member verifies their UPRM student ID, retrieves the backpack from storage, and returns it to the student. The system entry for the item is updated to Returned, closing the case.

==== Domain Attributes in Authentication
:author: Dylan M. Oliver Martinez


===== User
Person using the platform. Could be because they lost an item or found an item.

====== Characteristics
* *Discrete:* A user is a distinct entity with a unique account.
* *Dynamic:* User status, actions, posts, and interactions change over time.
* *Chaotic:* User behavior is unpredictable (they may lose items or find items).
* *Intangible:* In the system, the user is represented digitally as a profile.
* *Multi-dimensionality:* Users have multiple attributes (e.g., name, email, posts).

===== Password
Code selected by the user utilized to confirm the identity of the user.

====== Characteristics
* *Discrete:* A password is a specific string value.
* *Static:* It remains the same until the user changes it.
* *Intangible:* Exists only as data in the system.
* *One-dimensionality:* Usually a single attribute (string value), though it has properties like length and complexity.

===== Admin
User with the ability to ban other users, delete posts and accounts, and manually change data from profiles.

====== Characteristics
* *Discrete:* Admins are distinct user accounts with elevated privileges.
* *Dynamic:* Admins perform actions like banning users or deleting posts.
* *Intangible:* Represented digitally in the platform.
* *Multi-dimensionality:* Includes user attributes plus administrative permissions.

===== Guest
Users that can only view certain posts but cannot interact with them. Given to users that do not have an official UPR account.

====== Characteristics
* *Discrete:* Guests are a defined category of user.
* *Static:* Their permissions remain limited unless they create an account.
* *Dynamic:* They can browse content over time.
* *Intangible:* Represented as a temporary or restricted digital user state.
* *One-dimensionality:* Few attributes compared to registered users.

===== Item
An object that has either been lost by a user or found by a user.

====== Characteristics
* *Discrete:* Each item is a specific object.
* *Dynamic:* Item status can change (e.i., lost, found, returned).
* *Tangible:* The item exists physically in the real world.
* *Chaotic:* Items can be lost or discovered unpredictably.
* *Multi-dimensionality:* Attributes may include name, location, description, time lost/found, and owner.

==== Domain Concept Formation and Abstraction
:author: Tasnim Said-Khader

During the domain acquisition phase, several concrete entities and events were identified in relation to the lost-and-found process. These include specific types of items (like wallets, keys, laptops), location (like classrooms, libraries, study areas), and roles (like students, faculty, staff). While these domain description units are useful for understanding the problem space, repeatedly referencing each individual phenomenom can make the domain narrative unnecessarily detailed and difficult to maintain. 

To simplify the domain model and improve clarity across project documentation, these raw domain phenomena are abstracted into higher level domain concepts. These abstractions capture shared properties and behaviors among related entities and events, allowing the system domain to be described in a more concise and consistent manner.

===== Identified Abstractions
* Item

- *Type:* Entity
- *Phase:* Domain

An Item represents any personal object that may be misplaced or discovered within the campus environment.  
This abstraction groups specific belongings such as keys, identification cards, electronics, backpacks, and other personal property.

* Participant

- *Type:* Entity  
- *Phase:* Domain  

A Participant represents any individual who interacts with the lost-and-found process.  
This abstraction includes students, faculty members, and staff who may act as *Owners* of lost items, *Finders* of discovered items, or claimants seeking to recover belongings.

* Campus Location

- *Type:* Entity  
- *Phase:* Domain  

A Campus Location represents any physical area within the UPRM campus where an item may be lost or found.  
Examples include classrooms, study areas, libraries, laboratories, and common campus facilities.

* Item Report

- *Type:* Entity  
- *Phase:* Domain  

An Item Report represents the recorded description of a *Lost Item* or *Found Item* within the lost-and-found process.  
This abstraction consolidates the information necessary to enable identification, Matching, and eventual Recovery.

* Custody Context

- *Type:* Behavior  
- *Phase:* Domain  

The Custody Context represents the state in which an item is temporarily held or documented while awaiting identification or recovery by its rightful *Owner*.

* Recovery Process

- *Type:* Behavior  
- *Phase:* Domain  

The Recovery Process represents the sequence of actions through which a *Lost Item* progresses from initial *Reporting*, through *Matching* and *Claim Verification*, until *Recovery* or *Closure* occurs.

By introducing these abstractions, the Lost & Found domain can be described using consistent and reusable concepts rather than repeatedly referencing individual cases or object types. This improves the readability of the domain narrative and strengthens the conceptual structure of the system model.

:author: Angel Villegas (@angelvillegas1)

== Overview

This Lecture Topic Task applies the concept of structured domain acquisition to the Lost & Found system. Domain acquisition refers to the systematic elicitation and refinement of domain knowledge before formal modeling begins.

The objective is to demonstrate how structured acquisition improves both accuracy and completeness in the resulting domain description.

---

== Domain Acquisition Approach

Rather than beginning with predefined entities or database structures, the acquisition process began with constructed stakeholder personas representing realistic university scenarios. These personas included lost item owners, finders, administrative staff, and environmental observers.

The process followed a staged refinement strategy:

=== 1. Constructed Persona Narratives

Informal first-person accounts were created to simulate real-world campus experiences. These narratives captured behaviors such as delayed realization of loss, informal communication attempts, storage inconsistencies, and verification hesitation.

=== 2. Observation Extraction

Each narrative was decomposed into explicit observations. Observations focused on factual behavioral patterns rather than interpretation. This prevented premature abstraction and preserved raw domain characteristics.

=== 3. Derived Concept Formation

From repeated observations, reusable domain concepts were extracted (e.g., search ambiguity, retention window, platform fragmentation). This allowed patterns to emerge organically rather than imposing system assumptions too early.

=== 4. Concept Consolidation

Recurring themes were analyzed to detect lifecycle inconsistencies, communication gaps, behavioral asymmetries, and trust-related concerns.

=== 5. Formal Structuring

Only after concept stabilization were formal classifications introduced, including entity definitions, event definitions, behavioral constructs, and operational abstractions.

---

== Contribution to Accuracy and Completeness

Accuracy was improved by capturing multiple perspectives and distinguishing observations from interpretations.

Completeness was improved by incorporating behavioral, spatial, communication, and lifecycle dimensions rather than focusing solely on object tracking.

The resulting domain description is therefore traceable to structured conceptual extraction rather than arbitrary system modeling.

== Overview

This Lecture Topic Task applies the concept of domain facets to the Lost & Found system. Domain facets categorize domain knowledge into structured perspectives, allowing different aspects of the system to be analyzed without conceptual overlap.

== Domain Facets Explained

Domain facets separate domain knowledge into distinct viewpoints rather than treating it as a single undifferentiated structure. Common facets include intrinsics, business procedures, rules and regulations, support technology, management and organization, and human behavior.

---

== Application to the Lost & Found System

=== Intrinsics

The intrinsics facet captures fundamental domain elements such as Lost Item, Found Item, Report, Owner, and Finder. These elements define what exists in the domain independently of system implementation.

=== Business Procedures

This facet captures operational workflows including reporting, searching, matching, claim verification, recovery, and closure. These procedures describe how the domain evolves over time.

=== Rules and Regulations

This facet represents constraints governing behavior, such as authentication requirements, verification conditions before item return, and moderation policies.

=== Support Technology

Support technology includes enabling mechanisms such as authentication systems, notification processes, searchable storage, and lifecycle tracking. These mechanisms support domain operations but do not define domain meaning.

=== Management and Organization

This facet captures oversight responsibilities such as moderation, retention decisions, and administrative review processes that preserve institutional trust.

=== Human Behavior

The human behavior facet captures observed patterns including delayed reporting, informal communication attempts, privacy hesitation, urgency escalation, and non-reporting tendencies.

---

== Contribution to Domain Clarity

Applying domain facets clarifies the Lost & Found system by separating fundamental elements, workflows, constraints, technological mechanisms, oversight processes, and behavioral patterns.

This separation prevents mixing implementation decisions with domain logic and ensures conceptual coherence.

Through facet analysis, the domain becomes structured rather than fragmented, strengthening overall domain understanding.

==== [Lecture Topic Task] Domain Rules for the Lost & Found System
:author: Noel Colon Mena

===== Overview

This Lecture Topic Task defines the domain rules that govern how the Lost & Found system operates.

These rules help ensure that lost items are managed fairly, that claims are verified properly,
and that the system maintains consistent and reliable information.

===== Domain Rules

====== Rule 1: Item Status Consistency

An item must have exactly one status at any time.

Possible statuses include:

* Lost
* Claimed
* Returned
* Archived

_An item cannot be marked as both Lost and Claimed simultaneously._

====== Rule 2: Authenticated Reporting

Only authenticated users may report lost or found items.

_Users must be logged into the system before submitting item reports._

====== Rule 3: Single Claim per Item

An item may only be claimed by one user.

_Once a claim has been approved and the item has been returned, no additional claims can be submitted for that item._

====== Rule 4: Claim Verification

All claims must be verified before an item is returned.

_Verification must be performed by an administrator or Lost & Found member._

====== Rule 5: Claim-Item Relationship

Every claim must reference an existing item.

_A claim cannot exist without being associated with a previously reported item._

====== Rule 6: Reporter Cannot Claim Item

The user who reports a found item cannot claim ownership of that same item.

====== Rule 7: Required Item Information

Each item report must include minimum identifying information:

* Item Description
* Item Category
* Location where the Item was Lost/Found
* Date of the Report

_Reports missing required information cannot be submitted._

====== Rule 8: Archiving Unclaimed Items

Items that remain unclaimed for an extended period must be archived.

_Archived items remain stored in the system but are no longer visible in active search results._

===== Summary

These rules define key constraints for the Lost & Found domain. They help ensure that item reporting, claiming, and verification processes are handled consistently and securely.

==== [Lecture Topic Task] Domain Glossary & Shared Vocabulary for the Lost & Found System
:author: Anthony H Martinez-Gomez

*Framework:* Schütz-Schmuck, M. (2021). _Domain Engineering_. Department of Computer Science and Engineering, University of Puerto Rico at Mayagüez.

===== Overview

As the Lost & Found project grows, teams can unintentionally use different words for the same concept (e.g., "report" vs "listing", "claim" vs "request"). This creates ambiguity in requirements, UI text, and implementation. This Lecture Topic Task defines a shared vocabulary so that all documentation and development work uses consistent domain terms.

===== Naming Rules (Preferred Terms)

* Use *Report* for the act of submitting information into the system (lost or found).
* Use *Listing* for an entry that is visible in browse/search results (may be created from a report).
* Use *Claim Request* for a user’s request to retrieve an item.
* Use *Verification* for proof-checking before approving a claim request.
* Use *Sensitive item* and *Sensitivity level* for privacy/fraud-driven restrictions.
* Use *Admin* for the highest-privilege oversight role.
* Use *Staff/Moderator* for roles that assist with handling/verification but may have limited authority than Admin.

===== Glossary

====== Access Control
Rules that determine who can view information or perform actions in the platform, usually based on user role and item sensitivity.

====== Admin
A privileged role responsible for platform oversight (moderation, sensitive item handling, approvals, disputes, and policy enforcement).

====== Archived
A status indicating an item/listing is no longer active for recovery workflows (e.g., resolved, expired, disposed, or removed by policy).

====== Audit Log
A record of important events (e.g., edits, approvals, rejections, status changes) kept for accountability and dispute resolution.

====== Claim
The act of successfully retrieving an item after approval. +
*Do not confuse with:* *Claim Request* (the request step) and *Claimed* (the final status).

====== Claim Request
A user-submitted request to retrieve an item. Typically includes proof-of-ownership details and is reviewed by staff/admin.

====== Claimed
A status indicating an item has been released/returned to the verified owner.

====== Claimant
The user attempting to claim an item (the person submitting the claim request).

====== Confidential Detail
Information that should not be publicly shown due to privacy, safety, or fraud risk (e.g., ID numbers, serial numbers, exact storage location).

====== Dispute
A situation where multiple parties claim the same item or ownership is unclear and requires staff/admin resolution.

====== Found Item
An item that someone found and is reporting to the system for return to the owner.

====== Found Item Report
A report submitted by a user indicating they found an item (includes when/where and limited item description).

====== Guest
A user who is not logged in. Typically has the most restricted access.

====== Item
A physical object being tracked by the platform.

====== Item Category
A classification for items (e.g., electronics, documents, keys) used for filtering and for applying sensitivity rules.

====== Listing
An entry visible to users in browse/search results. +
*Do not confuse with:* *Report* (submission) vs *Listing* (published entry).

====== Listing Details
The set of fields shown to a viewer. For sensitive items, listing details may be limited based on role and sensitivity level.

====== Location (Broad)
A general location (e.g., building/area/zone) suitable for public display (example: "Library", "Engineering Building").

====== Location (Exact)
A specific location detail (e.g., room number, desk, exact coordinates, storage cabinet). Often restricted to staff/admin.

====== Lost Item
An item that the owner believes they lost and is trying to recover.

====== Lost Item Report
A report submitted by a user indicating they lost an item and providing identifying details they remember.

====== Minimum Necessary Disclosure
A principle that public listings should reveal only the minimum information needed for recovery, reducing fraud and privacy risks.

====== Moderator / Staff
A role that can help handle reports and verification processes, typically with less authority than Admin (depending on implementation).

====== Owner
The legitimate person the item belongs to.

====== Pending Verification
A status indicating an item is in a review stage (e.g., a claim request exists and requires proof checking).

====== Proof of Ownership
Information a claimant provides to demonstrate the item is theirs (e.g., unique marks, contents, unlocking device, accessory details).

====== Report
A submission entered into the system describing a lost or found item. +
*Do not confuse with:* *Listing* (public entry) and *Claim Request* (request to retrieve).

====== Reporter
The user who submitted a report (lost or found).

====== Restricted Field
A specific piece of data that is hidden from certain roles (field-level restrictions), such as serial number or ID details.

====== Role
A permission group assigned to users that determines what they can see/do (e.g., Guest, Registered User, Staff/Moderator, Admin).

====== Sensitive Item
An item that requires special handling because exposing details can create privacy, security, or fraud risks (e.g., IDs, keys, wallets, electronics).

====== Sensitivity Level
A classification describing how restricted an item’s information should be (example: Level 0 non-sensitive through Level 3 highly sensitive).

====== Status
A state representing where an item/listing is in its lifecycle (e.g., Available, Pending Verification, Claimed, Archived).

====== Verification
The process of checking proof-of-ownership before approving a claim request.

====== Verification Question
A detail asked during verification that should not be publicly visible (e.g., "What sticker is on the laptop?", "What’s inside the wallet?").

====== Visibility Rules
Rules that define what information is visible to each role, often influenced by sensitivity level.

====== Workflow
A defined sequence of actions in the platform (example: Report -> Listing -> Claim Request -> Verification -> Claimed/Closed).

===== Common Confusions (Quick Reference)

* *Report* vs *Listing*: Report is what a user submits; listing is what others browse/search.
* *Claim Request* vs *Claim*: request is the approval step; claim is the successful return.
* *Found* vs *Lost*: found is submitted by finder; lost is submitted by owner.
* *Location (Broad)* vs *Location (Exact)*: broad can be public; exact is usually restricted.
* *Sensitive item* depends on both item type and details exposed (not only item type).

==== Domain Attributes - Profile
:author: Keishlyany Sanabria (@keisanabria)

:toc: left
:toclevels: 3
:icons: font
:source-highlighter: highlight.js

*Framework:* Schütz-Schmuck, M. (2021). _Domain Attributes_. Department of Computer Science and Engineering, University of Puerto Rico at Mayagüez.

===== Overview

This document characterizes the domain attributes of the app's *Profile* section using the four-category framework from the UPRM domain attributes lecture. The app is a campus lost & found platform. A user's profile consists of four fields: *name*, *email*, *password*, and *phone number*. The analysis guides future modeling and design decisions by identifying how each field behaves with respect to continuity, dynamics, tangibility, and dimensionality.

A user's *email domain* also determines their permission tier: users who register with an institutional email address (`@upr.edu`) are granted full permissions, while users with a non-institutional email are restricted to view-only access. This distinction is documented where it affects each attribute category below.

===== Continuity vs. Discreteness

All profile fields are *discrete*. Each holds a value from a countable domain and only changes when the user explicitly submits a change. No profile field varies smoothly or continuously over time.

[cols="1,1,2", options="header"]
|======
| Field | Sub-type | Domain

| Name
| Textual (string)
| Non-empty Unicode string; constrained by length and character set.

| Email
| Textual (formatted string)
| RFC 5321-compliant address; membership in the set of syntactically valid email strings. The domain part additionally determines permission tier: institutional domain, gives full access; all other domains, gives view-only.

| Password
| Textual (opaque string)
| Arbitrary string subject to minimum-length and complexity rules; stored as a hash, never as plaintext.

| Phone number
| Textual / numeric (formatted string)
| E.164-formatted digit string; membership in the set of valid phone number patterns.
|======

NOTE: *Modeling implication:* All four fields map to constrained string types. Validation is rule-based (regex patterns, length bounds, format checks) rather than range-based or continuous. No interpolation or sampling logic is needed.

---

===== Statics vs. Dynamics

====== Static fields

No profile field is fully static in the strict sense, a user can change any of them. However, *name* is the most stable in practice: users rarely change their name and typically do so only under exceptional circumstances (legal name change, correction of a typo at registration). It sits at the static end of the spectrum.

[cols="1,2", options="header"]
|===
| Field | Rationale

| Name
| Set at registration; changes are rare, deliberate, and typically require re-verification. Treated as near-static for modeling purposes.
|===

====== Dynamic inert fields

The remaining three fields are *dynamic inert*: they hold a stable value indefinitely and transition only when the user explicitly navigates to account settings and submits a change.

[cols="1,2", options="header"]
|======
| Field | Stimulus

| Email
| User submits a new email address and confirms via verification link. Changing from a non-institutional to an institutional address (or vice versa) also triggers a permission tier change: full access from/to view-only.

| Password
| User submits current password and a new password through the change-password flow.

| Phone number
| User edits the phone number field and saves the change.
|======

NOTE: *Modeling implication:* All dynamic inert fields are safely stored in a persistent user record (for example, a `users` database table). No polling, background sync, or event streaming is needed to keep them current. Each change is fully determined by a user-initiated write operation. Email and phone number changes should trigger a re-verification step before the new value becomes active. Because the email domain drives the permission tier, any email change must also re-evaluate and update the user's `role` or `permission_level` field atomically, the two values should never be out of sync.

====== Dynamic active fields (not applicable)

No profile field changes autonomously or without a direct user action. If a future feature were to auto-populate the phone number from a campus directory or sync the name from an institutional identity provider, those sub-systems would be classified as *dynamic active programmable*, but the stored profile values themselves would remain inert.

===== Tangibility

All four profile fields are *intangible and precise*. They are abstract data values with no physical manifestation (they cannot be sensed or measured with an instrument), and their validity is fully determined by formal rules.

[cols="1,1,2", options="header"]
|======
| Field | Tangibility classification | Implication for validation and storage

| Name
| Intangible precise (free-form string)
| Validated by length bounds and permitted character set. No sensor noise; exact string comparison applies. Must support Unicode for international names.

| Email
| Intangible precise (formatted string)
| Validated by RFC 5321 syntax rules and confirmed by a verification email. Stored and compared case-insensitively for the domain part. The domain portion is additionally checked against the set of recognized institutional domains to determine permission tier (`full` vs. `view-only`); this check is exact and rule-based.

| Password
| Intangible precise (opaque string)
| Never stored in plaintext; stored as a salted hash (for example, bcrypt). Validated at entry by complexity rules; authenticated by hash comparison, not direct equality.

| Phone number
| Intangible precise (formatted string)
| Validated against E.164 format. Stored in a canonical normalized form to avoid duplicates from formatting variants (for example, `+17871234567` vs. `787-123-4567`).
|======

NOTE: *Storage implication:* Because all fields are intangible and precise, validation is entirely rule-based with no need to account for measurement uncertainty or sensor error. The most important implications are: (1) *password* must never be persisted as plaintext, only its hash; (2) *email* carries a secondary responsibility beyond identity, its domain part is the sole input to the permission-tier decision, so its canonical form must be stored consistently (case-normalized, verified) to ensure that permission derivation is deterministic and auditable.

===== Dimensionality

====== Zero-dimensional fields (atomic values)

All four profile fields are *zero-dimensional*: each holds a single, indivisible value with no meaningful internal structure from the profile domain's perspective.

[cols="1,1,1", options="header"]
|======
| Field | Type | Example value

| Name
| String
| `"Ana Rodríguez"`

| Email
| String (formatted)
| `"ana.rodriguez@upr.edu"`

| Password
| String → stored as Hash
| `"$2b$12$eW3fBs..."` (bcrypt hash)

| Phone number
| String (formatted)
| `"+17871234567"`
|======

====== One-dimensional fields (not present in current profile)

The current profile has no collection-valued fields. A future extension (such as a list of lost/found item reports submitted by the user) would be one-dimensional: an ordered sequence of report references linked to the profile record.

====== Multi-dimensional fields (flagged for future review)

If the app later surfaces a full history of a user's reported items, each with nested details (description, photos, status updates, timestamps), that structure would become multi-dimensional. It should be modeled as a separate `reports` entity related to the profile by a foreign key, rather than embedded directly in the profile record.

==== Classification of Static vs Dynamic Domain Elements in the Lost and Found System
:author: Iralys Sánchez Milián

===== 1. Introduction

In domain engineering, phenomena can be classified based on whether they change over time. Static elements do not change, while dynamic elements evolve due to events or internal behavior. Dynamic elements can further be categorized as inert (reacting only to external stimuli) or active (capable of initiating changes themselves).

This classification is essential for understanding system behavior, state transitions, and design decisions in the Lost & Found system.

===== 2. Domain Element Classification

[options="header"]
|===
| Domain Element | Type | Subtype | Justification

| Item Category
| Static
| N/A
| Categories (e.g., electronics, clothing) are predefined and do not change frequently or as part of system behavior.

| Report (Lost/Found Item)
| Dynamic
| Inert
| A report changes state (e.g., open, matched, resolved) only when users or admins perform actions.

| User Account
| Dynamic
| Inert
| User data (profile info, activity) changes only when the user or system updates it externally.

| Notification
| Dynamic
| Active
| Notifications can be generated automatically by the system (e.g., match found), without direct user action.

| Search Results
| Dynamic
| Inert
| Results change based on user queries or filters; they do not update unless triggered by input.

| Moderation Process
| Dynamic
| Active
| The system can automatically flag or process reports (e.g., spam detection), showing internal system-driven behavior.
|===

===== 3. Explanation of Classification

====== 3.1 Static Elements

Static elements are not time-dependent and are not affected by events. In this system, item categories remain constant and serve as reference data.

====== 3.2 Dynamic Inert Elements

Dynamic inert elements change only when triggered by external stimuli (e.g., user actions or admin input). Examples include reports, user accounts, and search results.

These elements:

- Require explicit input to change
- Do not evolve independently
- Represent controlled state transitions

====== 3.3 Dynamic Active Elements

Dynamic active elements can change based on internal system logic or autonomous behavior.

Examples include:

- Notifications generated automatically
- Moderation systems that flag inappropriate content

These elements:

- May act without direct user input
- Require monitoring and system logic
- Introduce complexity in system design

===== 4. Design Implications

This classification impacts system design in several ways:

- *State Management*: Dynamic elements require well-defined states and transitions.
- *Event Handling*: Inert elements rely on external triggers, while active elements require internal event mechanisms.
- *Automation*: Active elements necessitate background processes (e.g., notification services, moderation checks).
- *Data Modeling*: Static elements can be stored as fixed reference tables, while dynamic elements require lifecycle tracking.
- *Testing*: Active behaviors require additional testing for automated workflows and edge cases.

==== Data Consistency and System Guarantees in the Lost and Found Platform
:author: Jose Valentin (@jose-valentin)

The Lost and Found platform relies on consistent data and well defined system guarantees to ensure that reports behave predictably throughout their lifecycle. This section analyzes how consistency is maintained across the system and how guarantees are enforced to prevent invalid states and conflicting operations.

===== Overview

Data consistency refers to the requirement that all parts of the system reflect the same valid and up to date information at any given time. This includes consistency between the frontend interface, backend logic, and database storage.

System guarantees define the rules that ensure the system behaves correctly under normal operation. These guarantees restrict how data can change and ensure that all reports remain in valid states.

===== Consistency in Report Data

Reports are central entities in the system and must maintain consistent data across all interactions.

Key consistency requirements include:

* Frontend and backend consistency  
All data displayed to users must match the data stored in the backend. Any update performed through the interface must be validated and persisted correctly.

* Database consistency  
The database must always store valid and complete report data. Partial updates or invalid values must not be saved.

* Synchronization between users  
When multiple users interact with the same report, they must observe the same current state. The system must ensure that updates are reflected consistently for all users.

===== Report Lifecycle Consistency

Each report follows a defined lifecycle composed of discrete states:

* ACTIVE
* RESOLVED
* CLAIMED

These states represent the progression of a report from creation to completion.

Valid transitions include:

* ACTIVE to RESOLVED  
* ACTIVE to CLAIMED  
* RESOLVED to CLAIMED  

Invalid transitions must be prevented. For example:

* CLAIMED to ACTIVE  
* CLAIMED to RESOLVED  

Such transitions would violate the logical progression of the system and lead to inconsistent data.

These constraints are enforced through controlled state transition logic implemented in the backend.

===== Statics and Dynamics in Consistency

Consistency is closely related to how report attributes behave over time.

* Static attributes  
These values are expected to remain stable after creation:
** Title  
** Description  
** Category  
** Location  

* Dynamic attributes  
These values change over time and must be controlled:
** Status  

The report status exhibits dynamic inert behavior, meaning it only changes in response to external actions such as user interaction or administrative verification.

Ensuring consistency requires that dynamic attributes follow strict transition rules.

===== Scenarios Requiring Strong Consistency

Several scenarios require careful enforcement of consistency:

* Simultaneous updates  
Multiple users may attempt to update a report at the same time. The system must ensure that only valid updates are applied.

* Report modification after creation  
Edits must not violate existing constraints or create conflicting data.

* Status updates  
Changes to report status must follow valid transitions and reflect the correct lifecycle stage.

* Database interaction  
When inserting or updating reports, the system must ensure that the stored data matches the application state.

===== Mechanisms for Enforcing Consistency

The system enforces consistency through several mechanisms:

* Validation rules  
All input data is validated before being accepted. This prevents invalid or incomplete reports.

* Controlled state transitions  
The system restricts how report statuses can change, ensuring valid lifecycle progression.

* Backend verification  
Before applying updates, the backend checks the current state of the report to confirm that the operation is allowed.

* Atomic operations  
Updates are treated as single complete operations to prevent partial or inconsistent changes.

===== Impact on System Design

Consistency and system guarantees influence several aspects of the platform:

* Data integrity  
Ensures that all stored information remains accurate and meaningful.

* User trust  
Users depend on the system to provide correct and reliable information when reporting or claiming items.

* System reliability  
A consistent system behaves predictably, reducing unexpected errors and simplifying maintenance.

===== Conclusion

Data consistency and system guarantees are essential for maintaining a reliable Lost and Found platform. By enforcing validation rules, controlling state transitions, and ensuring synchronization between system components, the platform can maintain correct behavior and provide a dependable experience for its users.

===== Overview

Report verification and item claiming in the Lost & Found system can be understood as a domain process composed of interacting entities, events, functions, and behaviors. This process ensures that items are returned to their rightful owners while maintaining system consistency and preventing fraudulent claims. It combines structured system logic with human decision-making, reflecting both formal and informal aspects of the domain.

===== Verification Workflow and Domain Classification

The process begins when an item is reported. This is an event that creates a report entity within the system. The report contains relevant attributes such as item description, category, and location, forming part of the domain description. 

A user then submits a claim for the item. This is another event that introduces a new entity, the claim request, which is associated with the existing report. This establishes a relationship between two domain entities and initiates the verification process.

The claimant provides evidence to support ownership. This step functions as a function, since it transforms user-provided input into structured data that can be evaluated. Examples include identifying details or hidden characteristics of the item.

Next, the claim is reviewed. This step represents a behavior, as it involves a sequence of actions combining system operations and human judgment. The system organizes and displays the relevant data, while a moderator or staff member evaluates whether the evidence is sufficient to confirm ownership. This reflects a dynamic domain process where decisions depend on context rather than fixed rules.  

Finally, the system records the outcome as either approval or rejection. This is an event that causes a state transition in the report entity, such as moving from “pending verification” to “claimed” or remaining available. These transitions must follow controlled rules to maintain consistency across the system.  

===== System and Human Responsibilities

The system is responsible for handling structured and deterministic tasks. These include storing reports and claims, linking related entities, validating input data, and enforcing valid state transitions. These operations ensure that the domain remains consistent and that invalid states are prevented.

Human actors, such as moderators or staff, are responsible for evaluating evidence and making final decisions in ambiguous situations. Ownership cannot always be determined through automated logic, especially when information is incomplete or subjective. This introduces decision-based behavior that depends on human reasoning rather than purely formal rules.  

===== Challenging Scenarios

One challenging scenario occurs when multiple users submit claims for the same item. This creates a conflict where the system must manage multiple claim entities while ensuring that only one can be approved. The system maintains consistency by enforcing constraints, while human reviewers compare evidence and determine which claim is valid.

Another scenario arises when the item description is vague or incomplete. In this case, the system cannot reliably verify ownership using stored data alone. The process then depends more heavily on human judgment, requiring additional verification steps such as private questions or detailed descriptions. The system supports this by limiting visible information and requesting further input.

===== Impact on System Behavior

The verification process directly affects system behavior by controlling how reports transition between states and how conflicts are resolved. It ensures that only valid claims lead to ownership transfer, maintaining both data integrity and user trust. At the same time, it highlights the need for a balance between automated system logic and human decision-making within the domain.

==== Object Ownership and Access Control for Reports
:author: Adiel Soto

Object ownership defines which user has control over a report and determines what actions can be performed on it. Access control ensures that only authorized users can modify reports, maintaining system integrity and security.

===== Ownership Model

Ownership is established when a user creates a report. The creator becomes the owner and gains permission to edit or delete the report.

The ownership model includes:

- Owner: The user who created the report  
- Viewer: Any user who can see the report but cannot modify it  
- Admin: A privileged user who can override permissions when necessary  

Ownership may change after a successful claim, depending on system policy (e.g., item returned and report closed).

===== Domain Classification of Steps

The ownership process can be described and classified as follows:

[cols="1,2,2", options="header"]
|===
| Step | Description | Classification

| Report Created
| A user creates a report and becomes its owner.
| Event

| Permission Assignment
| The system assigns edit/delete rights to the owner.
| Function

| Report Access
| Other users can view but not modify the report.
| Behavior

| Admin Override
| An admin modifies or manages a report when necessary.
| Event

| Ownership Transfer
| Ownership may change after claim resolution.
| Behavior
|===

===== Access Control Enforcement

The system enforces access control through multiple mechanisms:

- Authentication: Verifies user identity before allowing access  
- Authorization: Determines what actions a user can perform  
- Permission checks: Ensure only owners or admins can edit/delete reports  
- Database rules: Restrict unauthorized updates at the data level  

Unauthorized modifications are prevented by validating user roles before any update operation is executed.

===== System vs Human Responsibilities

System-driven actions include:
- Verifying user identity (authentication)  
- Enforcing permission rules  
- Blocking unauthorized access attempts  
- Updating ownership data after valid transitions  

Human-driven actions include:
- Creating reports  
- Editing or deleting owned reports  
- Submitting claims  
- Admin reviewing and resolving disputes  

===== Complex Scenarios

[discrete]
====== Scenario 1: Anonymous Reports

A report is submitted without user identification.

Challenges:
- No clear ownership for editing or deletion  
- Increased risk of misuse or false reports  

System Handling:
- Limit editing capabilities  
- Assign temporary or restricted ownership  
- Require verification before allowing claims  

[discrete]
====== Scenario 2: Disputed Ownership

Multiple users claim ownership of the same item.

Challenges:
- Determining the rightful owner  
- Preventing unauthorized edits during the dispute  

System Handling:
- Lock report editing during dispute  
- Require evidence from claimants  
- Allow admin to resolve and assign final ownership  

===== Impact on System Behavior

Ownership and access control directly affect system security and reliability:

- Prevent unauthorized modifications  
- Protect user data and report integrity  
- Enable controlled collaboration between users  
- Ensure fair resolution of claims and disputes  

A well-defined ownership model strengthens trust in the system and ensures consistent behavior across all report interactions.
