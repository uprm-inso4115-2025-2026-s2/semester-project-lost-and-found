=== *Requirements Specification & Documentation*

==== Requirements Traceability and Inventory Lifecycle
:author: Adriel Bracero Gonzalez

===== Executive Summary
This lecture topic task connects *requirements traceability* to the Inventory and Item Lifecycle design for the Lost and Found application. The purpose is to show how requirements should be linked back to their sources, mapped forward to lifecycle states, and verified through tests or review. In the project, traceability helps the team keep track of why each feature exists, which stakeholder or risk motivated it, and how it supports the inventory flow from reported to disposed.

This document builds directly on the prior work already completed for the project: stakeholder analysis, inventory lifecycle research, search/tagging/filtering research, and risk assessment. The result is a structured requirements traceability matrix (RTM) that can be used during development, testing, and future change requests.

===== Scope and Objective
*Scope:* Traceability for the inventory lifecycle, including item intake, cataloging, storage, claim handling, verification, retention, disposal, search/filtering, privacy, and audit logging.  

*Objective:* Define a clear RTM that links requirements to source documents, lifecycle states, and verification methods so the team can check coverage, detect gaps, and reduce ambiguity.

===== Why Traceability Matters
Requirements traceability is useful because it answers four questions:
- Where did this requirement come from?
- Which lifecycle state or feature does it affect?
- How will we verify it?
- What breaks if we remove it?

For a lost-and-found system, traceability is especially important because the inventory lifecycle touches privacy, safety, ownership verification, custody logging, and eventual disposal. A missing requirement in any of those areas can create real operational risk.

===== Traceability Flow
[source,asciidoc]
----
Stakeholder need / risk / requirement source
                ↓
         Requirement statement
                ↓
      Inventory lifecycle state(s)
                ↓
      Design feature / user story
                ↓
      Verification method / test
----

===== Source Legend
To make the RTM easier to read, the source codes below are used in the matrix:

- *STK* = stakeholder analysis and personas
- *INV* = inventory lifecycle research
- *SFR* = search / tagging / filtering research
- *RISK* = risk assessment research
- *LEG* = legal / records / retention needs

The table below shows how each lifecycle state is covered by the RTM.

|REQ-03, REQ-04, REQ-05, REQ-09, REQ-10

|Disposed
|REQ-08, REQ-09, REQ-10
|Disposal must respect hold periods, keep history, and allow only valid final transitions.
|===

===== How Requirements Traceability Helps the Project
Requirements traceability improves the project in three ways:
- It keeps requirements aligned with stakeholder needs and lecture concepts.
- It reveals missing coverage before coding starts.
- It makes later change management easier because the team can see what a requirement depends on and what it affects.

For the Lost and Found system, this is especially useful because features like claim verification, custody logs, privacy controls, and disposal rules all depend on one another. Traceability helps the team avoid building isolated features that do not support the full lifecycle.

====== Functions
sign up: refers to the action of a new user creating an account

create account:   function that creates a new user account; this account uses the phenomena of username, email, phone number, and password 

check duplicate details: function that checks if there exists another of a username, email, or phone number in the database

verify email: function that sends an email to the users email address, to verify that the account belongs to the owner of the specified email address 

log in: refers to the action of an already existing user accessing their account

====== Phenomena 

account:  person using the platform; could be because they lost an item or found an item

username: the string that would be used an account

email: digital address that will be used to identify an account and for other users to communicate with each other

phone number: string that will be utilized to identify an account and for other users to communicate with each other

password: code selected by the user utilized to confirm the user's identity 

====== Other Concepts:

enter: type a username, email, or phone number into its respective field. When the account is created, it will be registered  into the database

duplicate: a given username, email, or phone number already exists in the database
