==== Temporal Aspects of the Lost and Found Domain
:author: Jose Valentin

Time plays an important role in how a lost and found system operates. Most actions in the domain occur at a 
specific moment and the system must keep track of when those events happen. Reports are created at a 
certain time, items remain unclaimed for a period of time, and status changes occur as time passes. 
Because of this, the system must handle several temporal characteristics in order to function properly and keep information accurate.

One important temporal element is the timestamp of a report. When a user submits a report for a lost or found item, the system records the exact date and time of creation. 
This timestamp allows the system to keep reports organized chronologically and helps users determine how recent the information is. 
For example, a report created a few hours ago is likely more relevant than one created several weeks earlier. 
Timestamps also help the system maintain a history of actions performed on each report.

Another aspect is the time associated with when an item was lost or found. In many situations the user may report an item some time after the actual event occurred. 
Because of this, the system should store both the time when the report was submitted and the time when the item was believed to be lost or found.
Keeping these values separate helps the system represent real world situations more accurately.

Item expiration is another important temporal behavior. Lost and found systems cannot keep reports active forever. 
After a certain period of time, items may be removed from storage or transferred to another process according to institutional policies.
The system therefore needs a way to detect reports that have existed for too long and mark them as archived.
This prevents outdated reports from cluttering the active listings and improves the overall usability of the system.

Claim deadlines are also related to time. When someone reports that they have found an item, the original owner may need to claim it within a specific time window.
If the item is not claimed within that period, the item may be handled differently according to the rules of the lost and found service. 
The system may support this behavior by storing a claim deadline or by calculating one based on the report creation time.

Status changes within the system are another example of temporal behavior. Reports usually begin in an active state when they are first created. 
If the owner retrieves the item, the report transitions to a resolved state. Later on, if the report becomes outdated or the item is no longer available, it may be moved to an archived state.
Although these changes may be triggered by user actions, they are also influenced by how much time has passed since the report was created.

Notifications can also depend on time. For instance, the system could notify users when a newly reported item matches a report they previously submitted.
It could also send reminders if an item is close to reaching its claim deadline. 
In these cases timing is important because the information must reach users while the report is still relevant.

Temporal considerations influence the design of the domain model and the overall system architecture. 
The report entity must include attributes such as creation timestamps and possibly expiration related data. 
The system may also need periodic checks that identify outdated reports and automatically update their status.
By incorporating these temporal characteristics into the system design, the lost and found platform can more accurately reflect the way lost item management works in real life.

==== Lost & Found System – Example User Scenarios
:author: Diego A. Ríos Morales
:date: March 13, 2026

This section describes example user interaction scenarios for the Lost & Found system. These scenarios illustrate common behaviors within the platform, including reporting lost items, posting found items, submitting claims, and reviewing claims.

===== Introduction

The Lost & Found system supports multiple types of user interactions related to reporting, searching, and recovering items. The following scenarios present common flows that help define how users and administrators are expected to interact with the system.

===== Scenario 1: Reporting a Lost Item

*Actor:* User

. A user logs into the Lost & Found platform.
. The user selects "Report Lost Item."
. The user enters item details such as description, location, and date lost.
. The system saves the lost item report and makes it searchable.

*Result:* The lost item is stored in the system and can later be matched with found items.

===== Scenario 2: Posting a Found Item

*Actor:* Finder (User)

. A user finds an item on campus.
. The user logs into the platform.
. The user selects "Post Found Item."
. The user enters details about the item and where it was found.
. The system publishes the found item listing.

*Result:* The found item becomes visible to users searching for lost items.

===== Scenario 3: Submitting an Item Claim

*Actor:* User

. A user searches the platform for a lost item.
. The user finds a listing that matches their item.
. The user submits a claim request.
. The system records the claim and sends it for review.

*Result:* The claim is stored in the system and awaits verification.

===== Scenario 4: Admin Reviews a Claim

*Actor:* Administrator

. The administrator reviews submitted claim requests.
. The administrator verifies the claim information.
. The administrator decides whether the claim is valid.
. The claim is approved or rejected.

*Result:* If approved, the item can be returned to the owner.

==== Value-Cost Feature Prioritization using AHP
:author: Leanelys González Orama
:date: March 18, 2026

Using AHP (Analytic Hierarchy Process), we will determine the relative proportion each requirement contributes to a criterion (Value or Cost). These features will be derived from Epics 1 through 5 (E1-E5). For both value and cost, the following scale is utilized:

- 1 - contributes/costs equally
- 3 - contributes/costs slightly more
- 5 - contributes/costs strongly more
- 7 - contributes/costs very strongly more
- 9 - contributes/costs extremely more

The same steps are used for both value and cost: a comparison matrix is created and later normalized to obtain the relative value and relative cost of each respective feature in order to plot the value-cost diagram.

*E1 (Reporting) vs. E2 (Search) [Value: 3]:* E1 is "Slightly more valuable". As identified in the concept analysis, the Report is the fundamental "system representation" of a lost item. While Search (E2) is critical for discovery, it is functionally dependent on the existence of a structured database created by E1.

*E1 (Reporting) vs. E3 (Safe Claim) [Value: 5]:* E1 is "Strongly more valuable". The primary operational goal is to increase successful returns. Establishing visibility through reporting is a prerequisite for the entire recovery lifecycle; Safe Claim (E3) is a secondary security layer that only becomes relevant after a successful match has been initiated.

*E1 (Reporting) vs. E4 (Accessibility) [Value: 7]:* E1 is "Very strongly more valuable". E1 directly enables the core "Reporting" function that satisfies the primary need for coordination. The system can technically facilitate a recovery with poor UI, but it cannot facilitate any recovery without the data provided by E1.

*E1 (Reporting) vs. E5 (Admin) [Value: 7]:* E1 is "Very strongly more valuable" than E5. While E5 (Admin) is necessary for maintaining transparency and trust, it is a supporting function intended to prevent misuse rather than a primary driver of successful returns.
