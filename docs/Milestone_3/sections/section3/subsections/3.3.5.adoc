[.added]
===== Traceability Strategy Rationale

The project adopts a requirement-centered traceability strategy rather than a document-centered or code-centered traceability strategy. Functional requirements were selected as the primary traceability anchors because they represent the most stable connection point between domain behavior, interfaces, implementation constraints, and verification artifacts.

Bidirectional traceability was selected to support:

- impact analysis when requirements evolve
- validation that all requirements are implemented and verified
- easier identification of affected subsystems during maintenance
- consistency between functional requirements, interfaces, and testing artifacts

The project uses a medium-granularity traceability model. Individual functional requirements are linked to related features, interface requirements, machine requirements, and verification artifacts, while avoiding excessive fine-grained tracing at the class, method, or variable level.

This approach was chosen because:

- coarse-grained traceability would not provide enough detail for effective change analysis
- fine-grained implementation-level traceability would introduce high maintenance overhead
- medium-granularity traceability provides sufficient impact visibility while remaining maintainable throughout project evolution

====== Forward Traceability

The requirement <<REQ-REPORT-F-01>> propagates into multiple dependent system artifacts including domain requirements, interface requirements, machine requirements, search systems, matching systems, and verification mechanisms.

The Report Lost Item requirement interacts with multiple components of the system:

*Domain Requirements*

* *Reporting Requirements*
 
- <<REQ-REPORT-F-01>>: The system shall allow a registered UPRM community member to create a Report for a Lost Item, including sufficient descriptive attributes to support Matching (e.g., category, description, approximate location, date or time window).  
- <<REQ-REPORT-F-02>>: Each Report shall distinguish between public descriptive information and private verification information within each Report.  
- <<REQ-REPORT-F-03>>: Upon creation, each Report shall be assigned an initial status of "Active".  
- <<REQ-REPORT-F-05>>: The system shall associate each Report with its creator to support ownership, traceability, and controlled modification.  

* *Search and Discovery Requirements*

- <<REQ-SEARCH-F-01>>: The system shall allow users to search Reports based on keywords related to item description, category, approximate location, and date or time window.  
- <<REQ-SEARCH-F-02>>: The system shall allow filtering of Reports by category, general location, date, and status.  
- <<REQ-SEARCH-F-03>>: The system shall present search results in a manner that supports comparison between Lost Item and Found Item Reports for Matching purposes.  

* *Matching and Tracking Requirements*

- <<REQ-MATCH-F-01>>: The system shall support the identification of potential matches between Lost Item and Found Item Reports based on descriptive attributes.  
- <<REQ-MATCH-F-04>>: The system shall allow the Owner of a Lost Item to monitor the status of their Report (Active, Returned, Closed, Expired).  
- <<REQ-MATCH-F-03>>: The system shall record status transitions from Active to Returned, Closed, or Expired.  

* *Claim Verification and Recovery Requirements*

- <<REQ-CLAIM-F-01>>: The system shall restrict marking an item as Returned to authenticated users involved in the Report.  
- <<REQ-CLAIM-F-02>>: The system shall support the use of private verification information to validate ownership before Recovery is confirmed.  
- <<REQ-CLAIM-F-03>>: Once Recovery occurs, the corresponding Report shall transition to "Returned" status.  

* *Closure Requirements*

- <<REQ-CLOSE-F-01>>: The system shall allow a Report to be manually closed if Recovery is no longer expected.  
- <<REQ-CLOSE-F-04>> / <<REQ-CLOSE-F-05>>: Closed Reports shall remain recorded for reference but shall be clearly distinguishable from Active Reports in search results.  

* *Administrative Oversight Requirements*

- <<REQ-ADMIN-F-01>>: The system shall allow authorized administrators to review Reports for inappropriate or misleading content.  
- <<REQ-ADMIN-F-02>>: Administrators shall be able to modify or remove Reports that violate institutional guidelines.  
- <<REQ-ADMIN-F-03>>: Administrators shall be able to override Report status in cases of misuse or verified dispute.

====== Verification and Test Artifacts

* *Report Creation and Ownership Verification*

- <<TEST-REPORT-01>>: Verifies that a lost item report can be created with all required descriptive attributes and is correctly bound to the authenticated owner.

- <<TEST-REPORT-04>>: Verifies that a found item report is created successfully and initialized with the correct active lifecycle state.

* *Report Editing and Access Control*

- <<TEST-REPORT-02>>: Verifies that the owner of a report can successfully edit and update their own report.

- <<TEST-REPORT-03>>: Verifies that non-owners are prevented from editing reports they do not own.

* *Privacy and Data Protection*

- <<TEST-REPORT-05>>: Verifies that sensitive or private information is not exposed in public views or stored incorrectly in the system.

* *Search and Discovery Validation*

- <<TEST-SEARCH-01>>: Verifies that reports can be retrieved using keyword-based search over descriptions and metadata.

- <<TEST-SEARCH-02>>: Verifies that filtering by category correctly narrows down search results.

- <<TEST-SEARCH-03>>: Verifies that search correctly retrieves reports matching textual and metadata criteria.

- <<TEST-SEARCH-04>>: Verifies that search functionality works independently of image uploads or attachments.

- <<TEST-SEARCH-05>>: Verifies that filtering by lifecycle status returns only reports matching the selected state (e.g., Active).

* *Moderation and Administrative Verification*

- <<TEST-MOD-01>>: Verifies that the system correctly detects and flags inappropriate or suspicious content automatically.

- <<TEST-MOD-02>>: Verifies that flagged reports are hidden from public visibility until reviewed.

- <<TEST-MOD-03>>: Verifies that report authors receive notifications when their report is flagged, approved, or removed.

- <<TEST-MOD-04>>: Verifies that authors can appeal, edit, and resubmit removed reports through the moderation workflow.

===== Traceability Maintenance Effort Assessment

Maintaining traceability links introduces moderate overhead during system evolution. Changes affecting reporting behavior typically require synchronized updates across multiple artifacts, including interface requirements, validation rules, database schemas, search functionality, matching logic, and verification tests.

Small modifications, such as adding a new report attribute or adjusting validation constraints, generally impact:

- report creation forms
- validation schemas
- database structure
- search and filtering systems
- associated verification tests

Larger policy changes, such as retention policies, privacy rules, or ownership verification requirements, propagate across additional subsystems including:

- matching and recovery workflows
- administrative oversight mechanisms
- public report visibility
- notification systems
- archival or deletion services

The selected medium-granularity traceability approach reduces maintenance complexity compared to fine-grained implementation-level traceability while still providing sufficient visibility for impact analysis and requirement verification.

This balance allows the project to maintain effective traceability without introducing excessive documentation overhead during iterative system evolution.
