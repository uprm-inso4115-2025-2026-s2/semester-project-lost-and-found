==== Requirements Traceability and Inventory Lifecycle
:author: Adriel Bracero Gonzalez

===== Executive Summary
This lecture topic task connects *requirements traceability* to the Inventory and Item Lifecycle design for the Lost and Found application. The purpose is to show how requirements should be linked back to their sources, mapped forward to lifecycle states, and verified through tests or review. In the project, traceability helps the team keep track of why each feature exists, which stakeholder or risk motivated it, and how it supports the inventory flow from reported to disposed.

This document builds directly on the prior work already completed for the project: stakeholder analysis, inventory lifecycle research, search/tagging/filtering research, and risk assessment. The result is a structured requirements traceability matrix (RTM) that can be used during development, testing, and future change requests.

===== Scope and Objective
*Scope:* Traceability for the inventory lifecycle, including item intake, cataloging, storage, claim handling, verification, retention, disposal, search/filtering, privacy, and audit logging.  

*Objective:* Define a clear RTM that links requirements to source documents, lifecycle states, and verification methods so the team can check coverage, detect gaps, and reduce ambiguity.

===== Why Traceability Matters
Requirements traceability is useful because it answers four questions:
- Where did this requirement come from?
- Which lifecycle state or feature does it affect?
- How will we verify it?
- What breaks if we remove it?

For a lost-and-found system, traceability is especially important because the inventory lifecycle touches privacy, safety, ownership verification, custody logging, and eventual disposal. A missing requirement in any of those areas can create real operational risk.

===== Traceability Flow
[source,asciidoc]
----
Stakeholder need / risk / requirement source
                ↓
         Requirement statement
                ↓
      Inventory lifecycle state(s)
                ↓
      Design feature / user story
                ↓
      Verification method / test
----

===== Source Legend
To make the RTM easier to read, the source codes below are used in the matrix:

- *STK* = stakeholder analysis and personas
- *INV* = inventory lifecycle research
- *SFR* = search / tagging / filtering research
- *RISK* = risk assessment research
- *LEG* = legal / records / retention needs

===== How Requirements Traceability Helps the Project
Requirements traceability improves the project in three ways:
- It keeps requirements aligned with stakeholder needs and lecture concepts.
- It reveals missing coverage before coding starts.
- It makes later change management easier because the team can see what a requirement depends on and what it affects.

For the Lost and Found system, this is especially useful because features like claim verification, custody logs, privacy controls, and disposal rules all depend on one another. Traceability helps the team avoid building isolated features that do not support the full lifecycle.

==== Claim Workflow Completeness Analysis
:author: Diego Rios Morales

===== Overview

The claim and verification workflow is one of the most important parts of the Lost & Found platform because it determines how users recover items and how ownership is validated. While the current workflow provides the foundation for submitting and claiming items, several scenarios remain incomplete or unclear. These gaps could affect the reliability, security, and usability of the platform if they are not addressed early in development.

This analysis identifies incomplete workflow cases, explains their potential impact, and proposes recommendations to improve the completeness of the domain model.

===== Incomplete Case 1: Multiple Users Claiming the Same Item

One unclear scenario occurs when multiple users attempt to claim the same lost item at nearly the same time. The current workflow does not clearly define how the system should prioritize or resolve competing claims.

Possible issues include:

* Two users submitting ownership claims simultaneously
* Conflicting verification evidence
* The original report owner responding to one claimant but not another
* Lack of a clear dispute resolution process

Without a defined process, the platform may create confusion between users or allow an incorrect ownership transfer.

====== Impact

* Increased risk of false claims
* User frustration due to unclear outcomes
* Potential trust issues within the platform
* Additional burden on administrators

====== Recommendation

The system should include a structured claim resolution process. Claims could be placed into a pending review state where supporting evidence is evaluated before ownership is confirmed. The workflow should also define how administrators intervene when disputes occur.

===== Incomplete Case 2: Unresponsive Users During Verification

Another incomplete workflow occurs when one side of the verification process becomes inactive. For example, a finder may stop responding after posting a found item, or the original owner may never complete verification steps.

Currently, the workflow does not clearly explain:

* How long claims remain active
* Whether claims expire automatically
* What happens to unresolved reports
* Whether reminders or notifications are sent

This creates uncertainty in the lifecycle of reports and claims.

====== Impact

* Reports may remain unresolved indefinitely
* Users may lose confidence in the platform
* System clutter may increase due to abandoned claims
* Administrators may need to manually manage inactive cases

====== Recommendation

The platform should define inactivity thresholds and automated claim expiration policies. Notifications and reminders should also be implemented to encourage users to complete the verification process before claims expire.

===== Incomplete Case 3: Insufficient Ownership Evidence

The current workflow assumes that users can successfully prove ownership of an item, but it does not clearly define what qualifies as acceptable evidence.

Examples of unclear situations include:

* A user provides vague item descriptions
* Multiple users describe the same item similarly
* No images or receipts are available
* The item is generic or common

Without clear requirements, verification decisions may become inconsistent.

====== Impact

* Increased chance of incorrect item transfers
* Difficulty maintaining fairness between users
* Reduced trust in the verification system
* Greater dependence on administrator judgment

====== Recommendation

The system should establish standardized ownership verification guidelines. Examples may include requiring:

* Distinctive item characteristics
* Proof of purchase
* Additional photographs
* Knowledge of hidden or unique item details

Defining these rules improves consistency and reduces ambiguity during the verification process.

===== Incomplete Case 4: False or Malicious Claims

The workflow currently does not fully describe how the platform handles intentionally false claims or malicious users attempting to abuse the system.

Potential issues include:

* Users repeatedly submitting fake claims
* Spam claim requests
* Attempts to steal valuable items
* Abuse of the verification process

====== Impact

* Reduced platform credibility
* Increased moderation workload
* Security and trust concerns for users
* Higher risk of disputes

====== Recommendation

The platform should include moderation and abuse prevention mechanisms such as:

* Claim attempt limits
* Reporting suspicious users
* Temporary account restrictions
* Administrative review tools

These protections would improve the overall reliability and security of the platform.

===== Workflow Completeness Improvements

The current claim workflow establishes a strong foundation, but several areas require additional clarification to fully support real-world usage. Expanding the workflow to address disputes, inactivity, insufficient evidence, and malicious behavior would significantly improve the reliability of the system.

A more complete workflow model should include:

* Clearly defined verification rules
* Claim expiration policies
* Dispute resolution procedures
* Administrative moderation tools
* Automated notifications and reminders

By addressing these incomplete scenarios early, the Lost & Found platform can provide a safer and more consistent experience for users while reducing ambiguity for developers and administrators.

==== Conclusion

The claim and verification workflow is a critical component of the Lost & Found platform, but several edge cases remain incomplete or insufficiently documented. Situations involving competing claims, inactive users, weak ownership evidence, and malicious behavior introduce risks that could negatively affect the platform if left unresolved. By improving workflow completeness and defining clearer system behaviors, the platform can become more secure, reliable, and easier to manage as development continues.
