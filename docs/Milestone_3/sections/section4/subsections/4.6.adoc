===== Report Lost Item Requirement
Reporting Requirements:

The system shall allow a registered UPRM community member to create a Report for a Lost Item.

The ID for a Lost Item Report: REQ-REPORT-F-01

*Scope:*

The requirement : REQ-REPORT-F-01, must be traced across:

- User Stories, Epics and Features
- Interface Requirements
- Machine Requirements
- Domain Requirements
- Test and Verification artifacts

===== Traceability Policy Rules:

- The Lost Item Requirement:REQ-REPORT-F-01,  much be linked to all related artifacts 
- Traceability links must be maintained and updated during evolution
- Any verification is traced back to REQ-REPORT-F-01 to confirm it is satisfied
- Any modification or change  to REQ-REPORT-F-01 must trigger impact analisys
- The requirement is fully traceable when all relevant interfaces, requirements and tests are captured and linked in the traceability table.

===== Traceability Links Between the Requirement and Related System Components 

====== Backward Traceability:

- US.REPORT.01 - Submit a Lost Item Report
- Epic E1: Reporting Lost and Found Items
- Feature F1.1 - Structured lost item submission
- F1.3 Image upload support
- F1.4 Edit and manage own reports
- Feature F1.5 - Automatic ownership binding

The Report Lost Item requirement interacts with multiple components of the system:

*Interface Requirements*:

- IR006 : The system must provide a public view for item details showing only public fields (category, description, photos, general location) and a prompt to log in to contact the owner
- IR009 : Report creation forms (Lost/Found) must include structured fields with validation, such as category dropdown, description, location picker, photo uploader, and private fields.
- IR014 :  An API endpoint POST /api/v1/reports must be available to create a new report (Lost/Found type).
           

*Machine Requirements*:

- SWRQ004 : The system must implement form validation using React Hook Form with Zod or Yup schema validation.
- SWRQ005 : The system must support image upload functionality with file size limit of 10MB per image for JPEG, PNG, and GIF formats.
- ENVRQ006 : The system must implement Row Level Security (RLS) policies in PostgreSQL for all data access.
- ENVRQ009 : The system must implement rate limiting on all API endpoints to prevent abuse

*Reporting Requirements*
 
 - DOMREP01: The system shall allow a registered UPRM community member to create a Report for a Lost Item
 - DOMREP03:Each Report shall include sufficient descriptive information to support Matching (e.g., category, description, general location, date).
 - DOMREP04 :The system shall distinguish between public descriptive information and private verificationinformation within each Report.
 - DOMREP05: Upon creation, each Report shall be assigned an initial status of "Active."


*Search and Discovery Requirements*

 - DOMSD01: The system shall allow users to search Reports based on keywords related to the item description.
 - DOMSD02: The system shall allow filtering of Reports by category, general location, date, and status.
 - DOMSD03: The system shall present search results in a manner that supports comparison between Lost Item and Found Item Reports for Matching purposes.


*Matching and Tracking Requirements*

- DOMMT01: The system shall support the identification of potential matches between Lost Item and FoundItem Reports
- DOMMT02: The system shall allow the Owner of a Lost Item to monitor the status of their Report (Active, Returned, Closed).
- DOMMT03: The system shall record status transitions from Active to Returned or Closed.


*Claim Verification and Recovery Requirements*

- DOMCVRR01: The system shall restrict marking an item as Returned to authenticated users involved in the Report.
- DOMCVRR02: The system shall support the use of private verification information to validate ownership before Recovery is confirmed.
- DOMCVRR03: Once Recovery occurs, the corresponding Report shall transition to "Returned" status.

*Clousure Requirements*

- DOMCR01: The system shall allow a Report to be manually closed if Recovery is no longer expected.
- DOMCR02: Closed Reports shall remain recorded for reference but shall be clearly distinguishable from Active Reports in search results.

*Administrative Oversight Requirements*
- DOMAOR01: The system shall allow authorized administrators to review Reports for inappropriate or misleading content.
- DOMAOR02: Administrators shall be able to modify or remove Reports that violate institutional guidelines.
- DOMAOR03: Administrators shall be able to override Report status in cases of misuse or verified dispute.

==== Dependent Systems:

- Search and Filtering Systems
- Matching System
- Notification System
- Claim and Recovery System

==== Change Scenarios
===== 1. Adding a New required field such as exact location or timestamp

*Effect:*

- IR009 form must be updated
- IR006 items public view must be updated
- SWRQ004 validation rules must be updated
- Database(Supabase) schema must be updated
- Search and filtering functionality affected

===== 2. Change in Image Upload policy such as reducing file  size limit or allowing more image formats

*Effect:*

- SWRQ005 must be updated
- IR009 UI must reflect new constraints 
- API validation must be modified

===== 3. Changing data Retention Policy such as auto-delete after a year

*Effect:*

- Search and Filtering systems must exclude expired reports
- ENVRQ006 must be updated 
- New requiremnet for scheduled deleition must be introduced
- IR006 must exclude old reports from view
- IR009 UI must inform users about report expiration
- IR014  API must handle expired/deleted reports correctly
- Database(Supabase) schema must be updated
- Matching system impacted due to loss of historical data

==== [Lecture Topic Task] Traceability and Change Impact Analysis in the Lost & Found System
:author: Victoria Miranda Osuna

===== Proposed Solution

-Define traceability links between requirements, software modules, databases, and user records.

    Create traceability links connecting lost-item reporting requirements to inventory management modules.
    Link claimant verification requirements to user-record databases and authentication components.
    Connect notification requirements to email or SMS notification services.
    Maintain links between software modules, test data, user manuals, and database records to support consistency management.
    Use dependency, revision, use, and derivation links to represent relationships between system components.

-Analyze how requirement changes affect dependent system components.

    Evaluate how modifications to item-tracking requirements impact inventory databases and notification workflows.
    Assess whether changes to claimant verification rules require updates to authentication modules and user records.
    Identify dependent software artifacts such as reports, logs, test data, and user documentation affected by requirement changes.
    Use traceability chains to localize and assess change impact across connected components.
    Apply change evaluation and prioritization to determine feasibility, risks, benefits, and implementation cost before consolidation.

-Use forward and backward traceability to track requirement dependencies and change impact.

    Use forward traceability to determine where a requirement is implemented within software modules, databases, and notification systems.
    Use backward traceability to identify why a requirement exists and where it originated.
    Follow dependency links horizontally and vertically to propagate requirement changes throughout the system.
    Track relationships between requirements, implementation artifacts, and supporting documentation to preserve consistency during system evolution.
