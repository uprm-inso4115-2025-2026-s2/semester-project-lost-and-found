=== *Requirements Satisfiability and Feasibility*

==== Notification System Feasibility Analysis
:author: Fernando Torres
===== Introduction

This section evaluates the feasibility and satisfiability of implementing an email-based notification system in the Lost and Found platform.

===== Functional Feasibility

The notification system is feasible because it relies on well-established technologies such as email services and backend event handling.

The system can generate notifications based on user actions such as account creation or item interaction.

===== Technical Feasibility

The system can be implemented using technologies such as Supabase and external email services.

The required infrastructure does not introduce significant technical complexity.

===== Data Requirements

The system requires:

* User email address
* Event type
* Notification content

===== Constraints

* Dependency on external email services
* Possible delays in delivery
* Invalid or missing user email data

===== Satisfiability

The system satisfies the requirement of informing users about important events in a timely manner.

===== Risks

* Duplicate notifications
* Emails marked as spam
* Failed delivery without retry

===== Conclusion

The notification system is feasible and can be implemented effectively with proper handling of constraints and risks.

==== Requirement Stability Classification
:author: Ivanier Bellido

This section presents a classification of system requirements based on their stability and importance during the requirements engineering phase. According to lecture principles on requirements satisfiability, stability refers to the classification of requirements based on their importance and resistance to change during the requirements engineering process.

Essential requirements are those that must be implemented for the system to function correctly. Worthwhile requirements significantly improve the system but are not strictly required for core functionality. Optional requirements provide additional enhancements but can be deferred without affecting system viability.

The following classification applies these concepts to the Lost & Found system:

[discrete]
===== Requirement Classification Table

[cols="1,3,1,4"]
|===
| ID | Requirement | Category | Justification

| R1
| Users must be able to report lost items
| Essential
| Core functionality of the system; without reporting, the platform cannot fulfill its purpose.

| R2
| Users must be able to report found items
| Essential
| Required to enable matching between lost and found items.

| R3
| Users must be authenticated using institutional email
| Essential
| Ensures system security, trust, and restriction to UPRM community.

| R4
| Users must be able to search and filter items by category, date, or location
| Essential
| Necessary for efficient discovery and recovery of items.

| R5
| Users can upload images of items
| Worthwhile
| Improves identification accuracy but system can function without images.

| R6
| System sends notifications for potential matches
| Worthwhile
| Enhances user experience and recovery speed but not strictly required.

| R7
| Administrative moderation of reports
| Worthwhile
| Helps maintain data quality and prevent misuse, but basic system can operate without it initially.

| R8
| System provides advanced filtering and sorting options
| Optional
| Improves usability but basic search functionality is sufficient for initial operation.

| R9
| Users receive automated alerts for new matching items
| Optional
| Adds convenience but does not affect core reporting and searching workflow.

| R10
| System supports analytics such as recovery rate or usage trends
| Optional
| Useful for evaluation and improvement but not required for system functionality.

|===

[discrete]
===== Discussion

The classification highlights that essential requirements are primarily related to core system operations such as reporting, authentication, and search capabilities. These form the minimum viable system.

Worthwhile requirements focus on improving usability, trust, and efficiency, such as notifications, moderation, and image support. These features enhance the system but can be implemented incrementally.

Optional requirements are mainly related to advanced features and analytics, which provide additional value but are not necessary during early development stages.

This classification supports better decision-making during development, helps prevent scope creep, and aligns implementation efforts with project priorities.

==== Implicit and Derivative Goals Traceback
:author: Ivanier Bellido

This section analyzes implicit and derivative goals of the Lost & Found system and establishes their relationship with explicitly defined requirements. According to lecture principles, implicit or derivative goals are objectives that are not directly specified as requirements but are expected outcomes of the system.

These goals typically originate from stakeholder needs, domain assumptions, and overall system intentions rather than from individual functional requirements.

The following analysis identifies key implicit goals and traces how they are supported by existing system requirements.

[discrete]
===== Identified Implicit Goals

The Lost & Found system is expected to achieve the following implicit goals:

* Increase recovery success rate of lost items  
* Reduce user frustration during the recovery process  
* Improve institutional trust in lost-and-found handling  
* Enhance coordination across campus entities  
* Promote consistent and structured reporting behavior  

[discrete]
===== Goal-to-Requirement Traceability

[cols="1,3,4"]
|===
| Goal | Supporting Requirements | Explanation

| Increase recovery success rate
| Item reporting (lost & found), search & filtering, image upload
| These requirements enable matching between lost and found items, increasing the likelihood of recovery.

| Reduce user frustration
| Search functionality, filtering, notification system
| Efficient search and timely updates reduce uncertainty and improve user experience.

| Improve institutional trust
| Authentication with institutional email, controlled visibility, moderation
| Ensures secure access, prevents misuse, and promotes confidence in the system.

| Enhance coordination across campus
| Centralized reporting platform, standardized data structure
| Provides a unified system that replaces fragmented communication channels.

| Promote structured reporting behavior
| Defined reporting forms, required data fields
| Encourages consistency and completeness in submitted reports.

|===

[discrete]
===== Analysis of Coverage

The mapping shows that most implicit goals are reasonably supported by existing requirements. Core functionalities such as reporting, authentication, and search directly contribute to achieving the system’s intended outcomes.

However, some gaps can be identified:

* Coordination across campus may depend on user adoption and integration with existing processes, which are not fully enforced by requirements.  
* Reduction of user frustration depends not only on functionality but also on usability and interface design, which may require further refinement.  
* Institutional trust also depends on consistent moderation and enforcement policies beyond basic technical constraints.  

[discrete]
===== Discussion

Implicit goals provide a higher-level perspective on system success and help evaluate whether the requirements collectively achieve meaningful outcomes. While individual requirements define system behavior, implicit goals ensure alignment with stakeholder expectations and domain needs.

This traceback analysis helps validate that the system is not only functionally correct but also aligned with broader objectives such as usability, trust, and effectiveness.

By explicitly documenting these relationships, the project improves traceability, supports better design decisions, and ensures that development efforts remain aligned with the intended purpose of the Lost & Found platform.
