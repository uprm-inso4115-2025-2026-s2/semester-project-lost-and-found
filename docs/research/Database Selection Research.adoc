= Database Selection & Data Modeling Strategy
:author: Ivanier Bellido
:issue: #93
:status: Proposed

== 1. Objective

The goal of this document is to choose an appropriate database and storage architecture for the Lost & Found platform.  
The decision is based on the needs identified in the A3 analysis and the expected behavior of the system.

Rather than selecting a technology only based on popularity or ease of use, we evaluated which option best supports the problem the project is trying to solve.

---

== 2. Relation to the A3 Analysis

From the A3 document we identified several important conditions:

[cols="1,2"]
|===
|A3 Observation | System Requirement

|Students frequently lose items across campus
|The system must handle frequent report creation

|Users cannot easily verify ownership
|Items must be searchable using description and category

|Current recovery process depends on manual communication
|A structured messaging relationship is required

|Matching depends on time and location context
|Database must support filtering and relational queries

|Users need a quick reporting process
|Backend responses must be efficient and simple
|===

Because of these points, the system benefits from structured and consistent data rather than loosely structured records.

== 6. Decision

The selected solution is **Supabase (PostgreSQL)**.

This option provides relational consistency, which helps model the relationships between users, reports, and messages.  
At the same time, it avoids the setup complexity of managing a database server manually.

This directly supports the A3 objective of improving item recovery by allowing reliable filtering and matching of reports.

---

== 7. Image Storage

Images will not be stored directly in the database.

Instead:

* Files stored in Supabase Storage
* Database stores only the image URL

Reasons:

* Reduces database size
* Improves query performance
* Allows CDN delivery
* Easier scaling
